# Benchmark 2026-08-08 — first baseline

First run of the `bench/` harness. Establishes what Skeid adds to a request, and finds the
ceiling where a single event loop stops keeping up.

## Setup

| | |
|---|---|
| Host | shared development box, Linux 6.1, other services resident |
| Upstream | `bench/fakellm`, `--ttft-ms 20 --tokens-per-second 1000 --tokens 64` |
| Proxy | `bin/skeid serve`, `bench/skeid.bench.yaml`, one node, `max_conns 256`, jsonlog usage |
| Client | `bench/llmbench`, `--tokens 64`, warmup 5, `nice -n 19 ionice -c3` |
| Rev | `46ce87c` plus the working tree of this session |

```bash
cd bench
./run-bench.sh --requests 100 --concurrency 1
./run-bench.sh --requests 320 --concurrency 16
```

The fake model's envelope was verified before anything else: baseline streaming TTFT p50 came
out at 20.27ms against a configured 20ms, and non-streaming total at 83.28ms against a
predicted 20 + 63×1 = 83ms. The instrument agrees with its own settings, so the numbers below
are about Skeid.

## Results

Latency to first content byte (p50 / p95 / p99, ms) and sustained throughput:

| Scenario | Baseline TTFT | Skeid TTFT | Δ p50 | Baseline req/s | Skeid req/s |
|---|---|---|---|---|---|
| json, c=1 | 83.28 / 83.35 / 83.55 | 88.17 / 89.25 / 92.68 | **+4.9 ms** | 12.0 | 11.3 |
| stream, c=1 | 20.27 / 22.27 / 33.79 | 23.94 / 26.31 / 35.15 | **+3.7 ms** | 11.9 | 11.4 |
| json, c=16 | 83.24 / 84.44 / 88.91 | 129.70 / 146.10 / 153.08 | **+46.5 ms** | 189.3 | 118.8 |
| stream, c=16 | 20.26 / 25.12 / 33.49 | 48.23 / 58.06 / 62.80 | **+28.0 ms** | 188.8 | 136.1 |

320 requests each at c=16, 100 each at c=1. No failures in any run.

## What this says

**Serial overhead is about 4 ms.** At c=1 Skeid costs 3.7–4.9 ms per request for routing,
admission, header forwarding, the upstream transaction and the usage write. Against a real
model that answers in seconds this is invisible; against a fast local model it is not nothing,
and it is the number to watch when changing anything on the request path.

**The ceiling is one CPU, and it arrives early.** At c=16 the fake upstream sustains 189 req/s
while Skeid tops out at 119–136, and TTFT roughly doubles to triples. Skeid is not blocking —
if it were, the p99 tail would be far worse than this and requests would be serialised behind
whole 83 ms responses — it is simply out of CPU in one process. That makes the prefork question
(karr #7) a measured question rather than a hunch, with the caveat that `max_conns` admission
is per-process state and changes meaning under N workers.

**Streaming holds up better under load than plain JSON.** 136 vs 119 req/s at c=16, and less
TTFT growth (+28 ms vs +47 ms). The relay hands bytes onward as they arrive instead of
assembling, decoding and re-encoding a whole response at the end, so the work is spread across
the response instead of landing in one lump on the event loop.

## What this run found

Streaming through Skeid was broken end to end, and had been. The client received correct
headers, a `200`, and an empty body; the log filled with `Transaction already destroyed`. Two
independent causes, both fatal on their own:

1. The relay wrote each chunk with `$c->write($bytes)` and no drain callback. A dynamic
   Mojolicious response finishes once its write queue empties, so the response ended after the
   first chunk.
2. The first read event fires with an *empty* chunk as soon as the upstream headers are parsed,
   and writing an empty chunk finalizes the response — so it ended even before that.

Fixed by queueing chunks and draining through `write_chunk` with a drain callback, finishing
only when the queue is empty and upstream is done, and skipping empty chunks. SSE frames are
now also buffered across read boundaries — a frame split between two reads used to be dropped,
and the frame most likely to be split is the last one, which is the one carrying usage.

Regression test: `t/23-proxy-stream.t`, verified to fail against the old relay. The empty-chunk
half does not reproduce through a Mojolicious upstream; `fakellm` reproduces it reliably, which
is a fair summary of why this harness exists.

## Where the overhead actually is

Follow-up runs on the same setup, json, c=16, 320 requests, 64 tokens. Since the fake upstream
can serve 189 req/s at this concurrency, anything below that is the proxy being the constraint,
and `1 / req/s` is then the serialized time each request occupies in the event loop.

| Configuration | req/s | TTFT p50 | serialized ms/req |
|---|---|---|---|
| No proxy (baseline) | 188.1 | 83.3 ms | — (upstream-limited) |
| Minimal Mojolicious pass-through | 152.3 | 99.1 ms | 6.57 |
| Skeid, one process | 128.1 | 120.4 ms | 7.81 |
| Skeid, prefork 4 workers | 177.7 | 87.2 ms | — (upstream-limited again) |

The minimal proxy forwards the body upstream and returns the response: no routing, no
admission, no usage, no key resolution, no translation. It costs 6.57 ms/request. Skeid costs
7.81. **Everything Skeid does of its own — routing, admission, header handling, usage
accounting, JSON decode and re-encode — is 1.2 ms, about 16% of its per-request cost.** The
other 6.6 ms is what a Perl process running two HTTP stacks per request costs.

Three things were measured and found *not* to be the problem:

- **Usage accounting is free.** jsonlog dir mode 128.1 req/s, file mode 130.7, no usage store
  at all 129.8 — all within noise of each other. Moving the usage write off the request path
  would buy nothing.
- **Upstream connection reuse is worth ~5%.** Skeid was opening a fresh TCP connection per
  request (verified: 100 requests left 100 `TIME-WAIT` sockets), for two reasons — the client's
  hop-by-hop `Connection: close` was forwarded upstream, and `Mojo::UserAgent` pools only 5
  connections by default while serving 16 concurrently. Both fixed; json throughput moved
  118.8 → 125.3 req/s. Worth doing (forwarding hop-by-hop headers is wrong regardless) but not
  the lever.
- **Micro-optimising the routing path cannot pay.** The whole budget it could come out of is
  1.2 ms.

**Workers are the lever.** The same app under `Mojo::Server::Prefork` with 4 workers reaches
177.7 req/s at c=16 with TTFT p50 87.2 ms — overhead falls from +37 ms to +3.9 ms, and at c=32
it scales to 350.2 req/s. The concurrency penalty is entirely one process on one CPU.

The blocker is not the flag, it is the semantics: `inflight` and `max_conns` are per-process
state, so N workers admit up to N × `max_conns` to a node that can serve one number. That is
the design question karr #7 has to answer before a `--workers` flag ships.

## Not measured

Real models, GPU contention, TLS, anything across a network, cold start, admission behaviour at
a realistic `max_conns`, the KeyBroker path (no broker configured — a vault round-trip per
request would land squarely on these numbers, see karr #3), and any database-backed usage store.
Every one of those is a separate run.
